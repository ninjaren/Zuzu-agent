🖼️ llava 讀圖：圖片怎麼變成文字

本專案有兩條觸發路徑，最後都走到同一種 API 請求，差別在「誰決定要不要看圖」——這個差異會直接影響你怎麼除錯。

路徑一：工具呼叫（大腦主動要求）

def analyze_image(path, question="請詳細描述這張圖片的內容"):
    p = _safe_path(path)                         # 路徑安全檢查
    if not p.exists():
        return f"檔案不存在：{p}"
    if p.suffix.lower() not in SUPPORTED_FORMATS:
        return f"不支援的圖片格式：{p.suffix}"

    image_b64 = base64.b64encode(p.read_bytes()).decode("utf-8")
    resp = requests.post(OLLAMA_URL, json={
        "model": VISION_MODEL,                    # llava:7b，不是 qwen3
        "messages": [{"role": "user", "content": question, "images": [image_b64]}],
        "stream": False,
    })
    return resp.json()["message"]["content"]

這是 qwen3 可以呼叫的工具之一（tools/vision.py 的 DEFINITIONS）。使用者問「這張圖裡有什麼」，qwen3 可以主動決定呼叫 analyze_image，走核心鏈路第四站的雙向溝通迴圈。

前面做了兩層防呆：_safe_path() 確保路徑沒超出允許範圍，檢查副檔名是否在支援清單內。

路徑二：前處理（使用者直接上傳圖片）

def analyze_image_b64(image_b64, question):
    resp = requests.post(OLLAMA_URL, json={
        "model": VISION_MODEL,
        "messages": [{"role": "user", "content": question, "images": [image_b64]}],
        "stream": False,
    })
    return resp.json()["message"]["content"]

這個函式不開放給大腦當工具呼叫，是 harness 自己在 build_messages() 裡直接呼叫——使用者上傳圖片時不需要等模型決定要不要看圖，直接先分析再說。

兩條路徑的差異比較

路徑一：analyze_image路徑二：analyze_image_b64
誰決定要看圖大腦自己決定Harness 自動觸發
圖片來源本機檔案路徑網頁上傳的 base64 資料
觸發時機agent_loop 的迴圈中途build_messages 一開始
對大腦可見是否，只會收到結果文字

關鍵：圖片要轉成 base64

Ollama 的 Chat API 不接受直接傳圖片檔案，要先轉成 base64 文字字串才能塞進 JSON——JSON 格式只能承載文字，沒辦法直接嵌入二進位資料。這也呼應「LLM 只認得文字」這件事：連圖片都得先變成文字編碼，才能在整套系統裡流動。

工作中真的會踩到的坑

⚠️ 兩條路徑各自有防呆，容易漏掉其中一條

路徑一有 _safe_path() 和副檔名檢查，路徑二（直接上傳）繞過了這些檢查——因為上傳的是 base64 資料，不是本機路徑，原本的路徑安全檢查根本用不上。如果之後要加防呆（例如限制檔案大小、檢查圖片格式有效性），容易只改到其中一條路徑，另一條被遺漏，這種「兩條路徑長得很像但其實防護不對稱」的情況，正是程式碼審查時最容易漏掉的地方。

⚠️ 誤判「視覺模型慢」其實是「圖片太大」

使用者上傳的原圖沒先壓縮，直接整張轉 base64 塞進請求，大圖片會讓請求變得很肥、傳輸和處理都變慢。第一次遇到這個問題時很容易怪到 llava 本身「推論太慢」，實際上常常是輸入資料太大，值得先做縮圖或壓縮再轉碼，而不是急著換更快的硬體。

🎓 深入機制（進階，可選讀）

llava 內部實際上長什麼樣子？base64 編碼的膨脹率怎麼算？這一節補上技術細節。

1. LLaVA 的實際架構：三個元件組成

LLaVA 出自 Liu et al.（2023）論文《Visual Instruction Tuning》，由三個元件串接：

元件作用
① 視覺編碼器通常是 CLIP 的視覺編碼部分（ViT），把圖片轉成向量表示
② 投影層小型神經網路（通常是簡單 MLP），把視覺向量轉換到語言模型能理解的維度
③ 語言模型骨幹接收轉換後的視覺向量，像處理文字 token 一樣生成回答

巧妙的地方：視覺編碼器通常直接沿用預訓練好的，真正需要訓練的主要是投影層——相對輕量，這也是為什麼 LLaVA 能用相對少的訓練資源，把既有的視覺能力和語言能力接在一起。

2. 訓練方式：Visual Instruction Tuning

「Instruction Tuning」指訓練資料用指令—回應配對的形式（跟 SFT 階段同一類方法），只是指令附帶一張圖片。透過大量這樣的配對，模型學會根據圖片內容正確回應指令，而不只是單純描述畫面。

3. Base64 編碼的真正機制與代價

原始資料：3 bytes（24 bits） 編碼後：4 characters（每個字元代表 6 bits，4×6=24 bits） → 編碼後的文字大小 ≈ 原始資料的 4/3 倍（約增加 33%）

一張 3MB 的圖片轉成 base64 後約膨脹到 4MB，全部要塞進請求的 JSON 裡傳輸——這也是上面「踩雷」第二條背後的量化原因，處理大量圖片的系統通常會先壓縮或縮圖再轉碼。

4. Pipeline 架構 vs End-to-End 架構

本專案「llava 轉文字 → qwen3 接手」屬於 Pipeline（管線）架構——任務拆成獨立階段，前一階段輸出是後一階段輸入。原生多模態模型是 End-to-End（端到端）架構——整個任務在單一模型內一次完成。

一個情境理解根本差異：照片裡是「一台紅色轎車停在藍色轎車旁邊，紅色車後保桿有個小凹痕，車牌寫著 ABC-123」。

🗣️ Pipeline（本專案）：朋友幫你看完照片，口頭說「有兩台車，一紅一藍」——你問「車牌幾號」永遠答不出來，因為照片本身你從沒看過，朋友沒講到的細節永遠消失。

👁️ End-to-End：你自己拿著照片一邊看一邊答，問到車牌可以重新盯著那個角落看，因為原始照片一直在你手上，沒被壓縮成一句話就丟掉。

關鍵就在這裡：文字是一個很窄的瓶頸。沒寫進描述裡的東西，對 qwen3 來說就是不存在，再會推理也補不回來。

Pipeline（本專案）End-to-End（原生多模態）
資訊損耗⚠️ 中繼表示（文字描述）是瓶頸，沒寫到的細節永久消失✅ 內部用連續向量傳遞，理論上保留更多原始資訊
各階段可否獨立替換✅ 容易（換 VISION_MODEL 即可）❌ 困難（整個模型要重新訓練或整個換掉）
除錯難度✅ 容易定位是哪一階段出錯❌ 整個模型是黑盒
整體延遲⚠️ 多個階段的時間會疊加✅ 通常單次推論即可
