🔍 RAG 檢索整合：兩種記憶怎麼合併

RAG = Retrieval-Augmented Generation。先搜尋相關資料，再把資料塞進提問一起給模型看——這一步合併得不乾淨，前面兩站做得再好也沒用。

retrieve()：語意搜尋

def retrieve(query, top_k=3):
    count = _col.count()
    if count == 0:
        return []                              # 資料庫是空的，直接跳過
    vec = _embed(query)
    if vec is None:
        return []                              # embedding 模型未就緒，跳過 RAG
    results = _col.query(query_embeddings=[vec], n_results=min(top_k, count))
    return [{"user": meta["user"], "assistant": meta["assistant"]} for meta in results["metadatas"][0]]

把這次問題也轉成向量，去向量資料庫找意思最接近的過去對話，本專案設 RAG_TOP_K = 10。min(top_k, count) 這個小細節容易被忽略——避免請求撈取的筆數超過資料庫實際存在的總筆數，不然 ChromaDB 會報錯，而且通常是在資料庫剛建好、資料還很少的早期測試階段才會踩到。

合併進 build_messages()

recent = history[-(RECENT_TURNS * 2):]
recent_texts = {m["content"] for m in recent}

retrieved = rag.retrieve(query, top_k=RAG_TOP_K)
relevant = [
    f"Q: {t['user']}\nA: {t['assistant']}"
    for t in retrieved
    if t["user"] not in recent_texts          # 排除跟「短期記憶」重複的內容
]

msgs = [{"role": "system", "content": SYSTEM_PROMPT}]
if relevant:
    msgs.append({"role": "system", "content": "以下是過去相關的對話紀錄，供你參考：\n\n" + "..."})
msgs.extend(recent)

RAG 撈回來的內容先過濾掉跟短期記憶重複的部分，再以獨立的 system 訊息插入，不混進使用者/助理的對話流，避免污染對話格式。

為什麼要去重、為什麼用獨立的 system 訊息

  • 🔁 去重：RAG 搜尋到的內容如果剛好也在最近 10 輪裡，重複塞進去只是浪費 token
  • 📦 獨立插入：直接把舊對話塞進對話串，模型可能搞混「這是剛剛講的」還是「很久以前的參考資料」，獨立 system 訊息讓模型清楚知道這是背景資料

完整流程圖

使用者問題
   ├─ ① 短期記憶：history 最近 10 輪 ──────┐
   ├─ ② 長期記憶：ChromaDB 語意搜尋（去重）──┤→ ③ 合併 → 送進 LLM
   └─ system prompt ────────────────────────┘

最終送給 LLM 的訊息大概長這樣

[
  {"role": "system", "content": "你是 ZuZu..."},                          ← 固定規則
  {"role": "system", "content": "以下是過去相關的對話紀錄：\nQ: ... A: ..."},   ← RAG 撈回來的（如果有）
  {"role": "user",      "content": "（10輪前的問題）"},                     ← 短期記憶
  {"role": "assistant", "content": "（10輪前的回答）"},
  ...（中間省略）...
  {"role": "user",      "content": "今天台北天氣如何？"}                    ← 這次的新問題
]
到這裡，記憶跟 RAG 的機制已經組起來了。它跟主線地圖的 ①LLM ⇄ ②API/Tokenizer 銜接的地方是：這裡整理好的 messages，正是透過 API 打包送進模型的那包內容。但「組起來」不等於「夠準」——下一站處理的正是這個問題。

工作中真的會踩到的坑

⚠️ 以為「越相關的資料塞越多」答案就會越好

RAG_TOP_K 調太高，撈回來的內容會混進一堆只是「勉強相關」的舊對話，稀釋掉真正重要的資訊，跟直接塞太多對話歷史是同一類問題——「多」不等於「有幫助」，這個直覺很容易在調參數時被忽略，覺得「多撈一點總是比較保險」。

⚠️ 舊資料跟新說法衝突時，沒設計任何處理原則

如果使用者在不同時間點對同一件事給過不一致的資訊（例如前後兩次講了不同的偏好），RAG 撈回來的舊內容可能跟這次的新說法衝突，系統提示詞沒特別交代的話，模型要自己賭「以哪個為準」，結果不保證穩定。這種情境在測試階段很少出現，通常是系統跑了一段時間、累積足夠多舊資料之後才會浮現，值得提早在提示詞裡寫清楚「以最新內容為準」這類原則。

🎓 深入機制（進階，可選讀）

RAG 是一個有正式論文出處、有標準三階段流程、有專門評估指標的技術框架，不是本專案自創的做法。

1. RAG 的正式出處

RAG 這個名稱和方法出自 Lewis et al.（2020）的論文《Retrieval-Augmented Generation for Knowledge-Intensive NLP Tasks》。要解決的問題：純粹依賴參數裡的知識有兩個限制——知識隨訓練時間點凍結、模型容易在不確定時幻覺。RAG 讓模型在生成前先查資料，把查到的真實資料當依據。

2. RAG 標準流程的三個階段

階段做什麼本專案對應
① Indexing原始資料切塊、轉成向量、存進向量資料庫，通常離線批次處理store_turn()，但即時做（每輪對話結束立刻索引）
② Retrieval查詢轉向量，搜尋最相關片段retrieve()
③ Generation檢索內容和查詢一起交給 LLMbuild_messages() 把 relevant 併入 msgs

3. 跟「教科書版 RAG」的差異：Chunking 策略

典型 RAG 系統要處理切塊問題：片段太大檢索精準度下降，片段太小可能切斷上下文。本專案的「文件」是對話紀錄，天然以一輪對話為單位切塊，不需要額外設計切塊策略——這是結構化問答配對比處理任意長文件簡單的地方。

4. 檢索品質的正式評估指標

  • 📏 Precision@k：檢索回來的前 k 筆裡，有多少是真正相關的
  • 📐 Recall@k：所有真正相關的內容裡，有多少出現在前 k 筆裡

兩者互相取捨：調高 top_k 提高 Recall，但可能拉低 Precision——這正是上面「踩雷」第一條背後的量化解釋。

5. Dense Retrieval vs Hybrid Search

本專案用純粹的 Dense Retrieval——完全依賴 embedding 的語意相似度。生產級系統常搭配 Sparse Retrieval（如 BM25）一起用，稱 Hybrid Search：Dense Retrieval 擅長語意相近但用字不同的內容，但可能漏掉字面完全相符的精確匹配，這時 Sparse Retrieval 當補強保險，兩者結果加權合併。
