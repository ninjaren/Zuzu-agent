🗄️ 長期記憶：ChromaDB 向量資料庫

短期記憶只記得最近 10 輪，更久以前的內容要靠語意搜尋，不是關鍵字搜尋——這個差異決定了你能不能真的找回相關的舊對話。

什麼是向量資料庫

把每句話轉成一串數字（向量），意思相近的句子，數字也相近（兩個向量的「距離」比較短）。找「意思接近的過去對話」只要比較數字距離，不需要完全相同的關鍵字。

舉例：這次問「台北明天會下雨嗎」，資料庫裡存著一個月前的「新竹這週天氣如何」。這兩句話沒有任何一個字完全一樣，但語意搜尋能辨認出都在問天氣，傳統關鍵字搜尋很可能完全找不到關聯。

轉換文字成向量：Embedding

OLLAMA_EMBED_URL = "http://localhost:11434/api/embed"
EMBED_MODEL = "nomic-embed-text"   # 專門做嵌入的模型，跟對話模型是分開的

def _embed(text):
    resp = requests.post(OLLAMA_EMBED_URL, json={"model": EMBED_MODEL, "input": text})
    return resp.json()["embeddings"][0]

注意這裡用的是另一個模型 nomic-embed-text，不是 qwen3:8b——這跟多模態橋接子地圖「llava 專門看圖、qwen3 專門對話」是同一種分工思路：每個模型只做自己最擅長的事，harness 負責串起來。一段文字經過轉換會變成固定長度的浮點數陣列（例如 768 維），你不需要看懂這些數字，向量資料庫只負責比較兩組數字陣列的距離。

存進去：store_turn()

def store_turn(turn_id, user, assistant):
    vec = _embed(user)                      # 把使用者的問題轉成向量
    _col.upsert(
        ids=[turn_id],
        documents=[f"Q: {user}\nA: {assistant}"],
        embeddings=[vec],
        metadatas=[{"user": user, "assistant": assistant}],
    )

每輪對話結束後（app.py 的 /chat 端點）呼叫這個函式，存進 chroma_db/。幾個值得注意的細節：

  • turn_id 格式是 "{session_id}_turn_{n}"，每輪唯一
  • 用 upsert 而不是單純 insert，避免同一個 turn_id 重複寫入時出錯
  • 只對使用者的問題做向量化，答案本身不轉向量，只跟著存成 metadatas——因為搜尋時是拿新問題比對過去問過的問題，答案只是查到之後一起撈出來的內容
💡 如果 embedding 模型還沒下載好，_embed() 會回傳 None，store_turn() 和 retrieve() 都會安靜跳過，不會讓整個對話壞掉——這是刻意設計的容錯（Graceful Degradation）：長期記憶這個加分功能故障時，不該連累到正常聊天這個核心功能。

工作中真的會踩到的坑

⚠️ 忘記 embedding 模型要另外下載，上線前才發現 RAG 整個靜默失效

因為程式設計成「embedding 模型沒就緒就安靜跳過」，ollama pull nomic-embed-text 沒跑過的機器上，整個 RAG 功能會悄悄停擺，不會報任何錯誤，使用者也感覺不出差異——只是模型少了一塊本該有的參考資料。這種「優雅降級」的設計是對的，但代價是問題不容易被察覺，部署清單裡一定要把這個依賴明確列出來，不能只靠事後觀察。

⚠️ 以為 ChromaDB 不用管，資料夾一直長大也沒設上限

本專案用內嵌式 ChromaDB，資料直接存本機資料夾，不用另外架服務——這點很方便，但也容易讓人忘記它仍然是一份會持續成長的資料。對話量大了之後，chroma_db/ 資料夾會跟著變大，沒設清理或封存策略，遲早要處理「這份資料該留多久」的問題，這在專案剛起步時很容易被忽略。

⚠️ 把向量搜尋當成萬用搜尋，拿它處理需要精確匹配的查詢

向量資料庫擅長「意思相近」的模糊查詢，不擅長「完全符合條件」的精確查詢。如果使用者問的是一個精確的專有名詞或 ID，語意搜尋反而可能找不到或找錯，這是常見的誤用場景——先搞清楚你的查詢需求是「像不像」還是「對不對」，再決定要不要用向量搜尋。

🎓 深入機制（進階，可選讀）

「比較數字陣列的距離」背後有明確的數學定義和演算法。這一節講距離度量公式、ChromaDB 底層用的近似最近鄰演算法，以及 Embedding 模型是怎麼訓練出來的。

1. 距離度量：怎麼定義「意思接近」

餘弦相似度（Cosine Similarity）= (A·B) / (‖A‖ × ‖B‖) 歐氏距離（Euclidean Distance）= √( Σ (Aᵢ − Bᵢ)² )

餘弦相似度量的是向量方向夾角的接近程度（不管長短），介於 -1 到 1；歐氏距離量的是兩點的直線距離。文字嵌入通常偏好餘弦相似度，因為語意強度（向量長度）不一定有意義，重要的是方向代表的語意類別。ChromaDB 預設也用餘弦距離。

2. 為什麼不直接暴力比對每一筆資料

資料庫有 100 萬筆紀錄，每次搜尋都跟全部向量逐一比對距離（Brute-force / Exact Nearest Neighbor），運算量隨資料量線性成長，資料一多就慢到無法接受。生產級向量資料庫改用 Approximate Nearest Neighbor（ANN）演算法，犧牲一點準確度換取數量級的速度提升。

ChromaDB 底層用 HNSW 演算法：預先把向量組織成多層次圖結構，搜尋從最頂層（節點稀疏、跳得快）開始，逐層往下導航到正確區域——像先看地圖找城市、再看街道找門牌，而不是一戶一戶敲門。

3. Embedding 模型是怎麼訓練出來的

給模型大量「正樣本配對」（語意相近的兩句話） 和「負樣本」（語意無關的句子） 訓練目標：正樣本配對轉換出來的向量距離越近越好，負樣本距離越遠越好

這叫對比學習（Contrastive Learning）。訓練後模型學會把語意而不是字面編碼進向量空間的幾何關係——這也是「台北明天會下雨嗎」vs「新竹這週天氣如何」即使沒有共同字，向量距離依然相近的原因。

4. 維度詛咒

向量維度越高理論上能表達的語意細節越豐富，但也會遇到維度詛咒（Curse of Dimensionality）：隨維度增加，高維空間裡任兩點的距離會漸漸「都差不多遠」，讓「誰比較近」的判斷力下降。Embedding 模型的維度數量（768、1536、4096）是刻意調校的平衡點，不是越高維越好。
