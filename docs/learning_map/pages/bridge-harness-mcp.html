🔌 Harness 和 MCP 中間發生了什麼

Harness 要先學會「MCP 這門語言」才能接上 MCP 插座。中間三層，跟第二站 LLM⇄Harness 橋接的三層概念相呼應——又是一組轉接器＋傳輸線＋講話規則。

Harness
   ⬇️ MCP Client（內建的插座轉接器，知道怎麼講 MCP 語言）
   ⬇️ Transport（傳輸線：stdio 本機管道，或 HTTP/SSE 網路連線）
   ⬇️ JSON-RPC（講話規則：tools/list 問有什麼工具、tools/call 呼叫工具）
MCP Server

第一層：MCP Client

Harness 本身不會天生懂 MCP，要先裝一小段程式叫 MCP Client，負責：

  • 跟 MCP Server 建立連線
  • 把 harness 的請求翻譯成 MCP 懂的格式
  • 把 MCP Server 回應的結果，轉換成 harness 原本就懂的格式
就像筆電沒有 USB-C 孔，要先裝一個轉接卡，之後才能插各種 USB-C 設備。MCP Client 就是那張轉接卡。

第二層：Transport

  • 🔌 stdio：MCP Server 其實是 harness 啟動的子程序，兩邊直接用管道傳資料，不走網路，速度快、也不用處理連線失敗
  • 🌐 HTTP/SSE：工具跑在遠端伺服器，透過網路連過去；SSE 讓伺服器可以主動推送資料，不用 harness 一直問

選哪種傳輸線取決於工具跑在哪裡——本機操作用 stdio，連到別人維護的雲端服務用 HTTP。

第三層：JSON-RPC

有轉接器、有線，兩邊還要講同一種語言。MCP 用 JSON-RPC 2.0：

// Harness 問：「你有哪些工具可以用？」
{"jsonrpc": "2.0", "method": "tools/list", "id": 1}

// MCP 伺服器答
{"jsonrpc": "2.0", "id": 1, "result": {"tools": [{"name": "read_file", ...}, ...]}}

// Harness 說：「幫我呼叫 read_file，參數是 xxx.txt」
{"jsonrpc": "2.0", "method": "tools/call", "params": {"name": "read_file", "arguments": {"path": "xxx.txt"}}, "id": 2}

// MCP 伺服器做完後答
{"jsonrpc": "2.0", "id": 2, "result": {"content": [{"type": "text", "text": "這是檔案內容：......"}]}}

每個請求帶一個 id，讓 harness 知道這個回應對應哪個問題——同時有多個請求在飛的情況下特別重要。

連線建立時的握手

MCP Client 第一次連上 Server 時，先做 initialize 交換雙方支援的版本和能力，確認完才開始真正問 tools/list。

目前本專案的狀況

qwen3_8b 專案目前尚未接 MCP，工具是用 Ollama 原生的 tools 參數（直接在同一個程序內呼叫，連 Transport 這一層都省了）。若未來要接，需要額外實作這三層——「進階方向」子地圖④有具體步驟。

工作中真的會踩到的坑

⚠️ 以為「接 MCP」是免費的標準化，沒算進維運成本

MCP Server 是獨立行程，代表你多了一個要啟動、要監控、要處理「掛掉怎麼辦」的執行單位。跟現在把工具函式直接 import 進同一個程序比，維運複雜度是真的升高了，不是只有「寫一個轉換函式」這麼輕鬆——這點在評估要不要接 MCP 時經常被低估。

⚠️ 同步阻塞的程式碼硬接非同步的 SDK

MCP SDK 是 async/await 寫法，本專案目前 agent_runner.py 是同步阻塞寫法。兩者混用時最常見的錯誤，是在同步函式裡直接呼叫 async 函式卻沒正確等待，結果協程根本沒執行完就被丟掉，你會看到「好像沒出錯，但工具結果是空的」這種特別難 debug 的狀況——這類問題通常不會在開發時就暴露，而是在某次邊界情況才現身。

🎓 深入機制（進階，可選讀）

「轉接器＋傳輸線＋講話規則」背後對應到位元組層級的訊息框架、行程隔離安全模型，以及兩套工具定義格式之間的結構化轉換。

1. stdio Transport 的訊息框架

MCP Client 和 Server 透過 stdio 溝通時，共用的是同一條位元組串流，沒有天然的訊息邊界。MCP 規格採用 Newline-delimited JSON：每則 JSON-RPC 訊息是一整行，用換行字元當結束標記。

這跟 MCP 明確借鏡的 LSP 不同——LSP 用更接近 HTTP 的 Content-Length 標頭。換行分隔簡單，但訊息內容不能包含未跳脫的換行字元；Content-Length 更穩健，但多一層解析複雜度。

2. Process Isolation：為什麼要用子程序

核心鏈路③提過最小權限原則，stdio Transport 本身就是這個原則的體現：MCP Server 是獨立的作業系統行程，不是被 import 進 harness 的程式碼：

  • 🛡️ 故障隔離：子行程崩潰不會拖垮 harness 主程式——這跟現在工具函式直接 import 進同一個程序形成對比，同程序內未捕捉的例外有可能讓整個 Flask 伺服器掛掉
  • 🔒 權限邊界：作業系統層級可以對子行程設更嚴格的資源限制，有明確的技術邊界，不只是依賴程式邏輯上的約定

3. Schema 轉換的形式化對應

MCP 的 inputSchema 和 OpenAI 的 function.parameters，底層都是 JSON Schema，核心結構幾乎一對一對應：

MCP 格式OpenAI / Ollama 格式
namefunction.name
descriptionfunction.description
inputSchemafunction.parameters

差異主要在最外層欄位命名和巢狀結構，是格式轉換問題，不是語意不相容的問題。

4. 錯誤如何跨行程邊界傳遞

MCP Server 發生錯誤時不能直接拋例外讓呼叫端 catch，因為兩個行程沒有共用記憶體。JSON-RPC 定義了標準錯誤物件：

{"jsonrpc": "2.0", "id": 2, "error": {"code": -32602, "message": "Invalid params", "data": {...}}}

MCP Client 收到後要自己判斷：這個錯誤該回報給模型看，還是該被 harness 攔截處理（例如判斷是不是連線中斷）。

5. 為什麼真正的 MCP Client 要用非同步寫法

MCP Client 要處理大量 I/O 密集的等待——等子行程啟動、等對方回應。同步阻塞寫法在管理多個 MCP Server 連線時會變成一個接一個排隊，非同步寫法能在等待某個連線的同時處理其他連線，大幅提升多工效率。
