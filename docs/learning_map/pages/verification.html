✅ 自我檢查機制（Self-Verification）

上一站提過模型會幻覺——很有自信地講錯話。這裡討論怎麼在 harness 這層抓錯。常見做法有兩種，差別在「有幾個大腦、有幾個 harness」，選錯方案最常見的後果是：花了額外成本，卻沒抓到真正會出包的那類錯誤。

為什麼需要自我檢查

LLM 本質是猜下一個字，沒有像計算機那樣保證正確的機制。常見出錯的地方：

  • 🔢 多步驟數學計算，中間某一步算錯
  • 📅 日期、時間相關推理（例如「三天前是星期幾」）
  • 📊 從工具拿回來的資料，摘要時斷章取義或理解錯誤
  • 🧩 邏輯推理鏈太長，中途忘記前面的條件

第一種：同一個 Harness，自己跟自己玩角色扮演

本專案採用此法。沒有第二個大腦，也沒有第二個 harness，同一個 harness 把同一顆大腦問了兩次，第二次換成「檢查員」的提問角度。

第1次打電話（人設：答題者）
Harness → LLM：「請回答這道數學題」
LLM → Harness：「答案是 42」

第2次打電話（人設：檢查員）← 還是同一個 harness、同一個大腦
Harness → LLM：「有人說這題答案是 42，你現在扮演嚴格的檢查員，幫我找錯」
LLM → Harness：「我檢查過了，第二步算錯了，應該是 45 才對」

這招有效的原因：第一次回答時模型在「生成答案」模式，注意力集中在把話講完；第二次用「檢查員」角色重讀一遍，是「審查既有內容」模式，兩種模式容易注意到不同種類的錯誤——這跟你自己寫完的程式碼隔天用審查者心態重看一遍，常常能抓到當下沒發現的 bug，是同一個道理。

第二種：Multi-agent，多個獨立 Harness 互相傳訊息

真的有多個獨立運作的 harness，各配一顆大腦（同一模型開多實例，或不同模型），彼此透過訊息溝通，例如一個負責寫程式、一個負責審查、一個負責統籌。成本更高，目前本專案沒有採用，「進階方向」子地圖有更詳細的設計討論。

自己跟自己檢查Multi-agent
大腦數量1 個（重複使用）可能多個獨立的
Harness 數量1 個2 個以上
溝通方式同一 harness 內部換提示詞重打電話不同 harness 之間互傳訊息
成本較低（多一次 API 呼叫）較高（每個 agent 都要跑完整流程）
適合情境抓明顯的計算/邏輯錯誤需要不同專業角度分工的複雜任務

對照本專案的程式碼

def _verify_answer(messages, answer, think):
    verify_messages = messages + [
        {"role": "assistant", "content": answer},                 # 把第一次答案塞回去
        {
            "role": "user",
            "content": (
                "請重新確認以上回答是否正確。"
                "重點檢查：數字計算、日期合理性、邏輯推導、工具資料引用。"
                "若有錯誤，直接給出更正後的完整答案；"
                "若答案正確，直接回覆原答案，不需要說「我確認了」或重複解釋。"
            ),
        },
    ]
    resp = requests.post(OLLAMA_URL, json={"model": MODEL, "messages": verify_messages, ...})
    return resp.json()["message"]["content"]

觸發方式：config.py 的 VERIFY_ANSWER（預設 False），或 /chat 端點傳 verify: true 做單次覆蓋。

提示詞設計的小細節

注意驗證提示詞特別交代「若答案正確，直接回覆原答案，不需要說『我確認了』」——這是為了避免模型在確認無誤時畫蛇添足加一堆廢話。這種「明確告訴它不要做什麼」的寫法，是提示詞工程裡實際有用、但很容易被忽略的技巧——多數人會花力氣寫「該做什麼」，卻漏了「不該做什麼」，結果輸出多了一堆沒意義的客套。

目前是「問一次檢查員」，不是「重複 5 次取多數決」的 self-consistency（「進階方向」子地圖②有詳細介紹）。目前決定保持現狀，先不升級。

工作中真的會踩到的坑

⚠️ verify 模式會讓每次回答都變慢，而且是使用者直接感受得到的那種慢

多一次完整 API 請求，實際耗時取決於提示詞長度和模型速度，估計約多 3-8 秒。這是正確性和速度的取捨，本專案設計成可選（預設關閉）是對的方向——把這種取捨直接暴露給使用者，比你自己猜一個「應該夠快」的預設值要可靠。

⚠️ 檢查員跟答題者是同一顆大腦，抓不住系統性的盲點

如果模型對某個知識有系統性誤解，兩次問都會得到一樣錯誤的答案——這是「自己跟自己檢查」的天花板：能抓隨機性失誤，抓不住模型本身知識上的盲點。想突破，要考慮多數決（靠機率分散隨機錯誤）或換一個不同的模型來檢查（避開同一套知識盲點）。容易踩的坑是：上線一段時間後發現某類錯誤一直沒被抓到，才回頭意識到問題不是「驗證沒開」，是驗證機制本身的天花板。

⚠️ 誤以為「有驗證」等於「答案一定對」

verify 模式提升的是正確率，不是保證正確——這句話聽起來像廢話，但實務上很容易被忽略：一旦系統裡有「驗證」這個詞出現，使用者（甚至你自己）很容易把信任程度拉得比實際該有的更高。把這個機制的真實能耐講清楚，比裝一個看起來很安心但實際效果有限的功能更重要。

🎓 深入機制（進階，可選讀）

幻覺和自我檢查在學術文獻裡都有正式的分類和研究方法。這一節介紹幻覺的正式分類，以及 Chain-of-Thought、Self-Consistency、Reflexion 這幾個關鍵研究方法。

1. 幻覺的正式分類

學術文獻（Ji et al. 2023 幻覺研究綜述）把幻覺正式分成兩類：

類型定義範例
Intrinsic Hallucination（內在幻覺）生成內容跟提供的來源資料直接矛盾工具回傳「今天氣溫 25 度」，模型摘要成「35 度」
Extrinsic Hallucination（外在幻覺）生成內容無法從來源資料驗證真假使用者問天氣，模型額外加「建議攜帶雨具」，但資料裡沒提到降雨

Intrinsic 幻覺理論上可以靠比對來源資料機械式抓出來；Extrinsic 更難處理，因為它不是「錯」，是編造了沒有根據的內容，需要仰賴模型自己判斷「這句話有沒有根據」。

2. Chain-of-Thought：先讓模型寫出步驟

Wei et al.（2022）的論文發現：引導模型一步一步想，而不是直接要答案，複雜推理題正確率會大幅提升。本專案的 think=True 本質上就是啟用這個能力。

原理：直接要答案，模型必須在一次生成裡隱性完成所有推理；先生成推理步驟，每一步結論會變成下一步猜測時可參考的上下文，相當於把一個困難問題拆成一串較簡單的小步驟，每步出錯機率都比一次到位低。

3. Self-Consistency：Chain-of-Thought 的強化版

Wang et al.（2022）的論文，正是「進階方向」子地圖②「多數決驗證」的學術出處：

1. 用同一個 Chain-of-Thought 提示詞，搭配較高的 temperature，取樣出 k 條不同的推理路徑 2. 每條路徑各自推導出一個最終答案 3. 對這 k 個答案做邊際化（marginalize）——統計出現頻率，選出最多路徑都同意的答案

核心論點：多條獨立推理路徑殊途同歸，這個答案正確的可能性遠高於單一路徑——跟統計學裡多次獨立測量取平均能降低誤差是同樣道理。

4. Reflexion：帶著失敗記憶的自我修正

Shinn et al.（2023）的論文提出更進階的概念：模型在任務失敗後用文字寫下「這次為什麼失敗、下次該怎麼改進」，存進記憶，下次嘗試同類任務時參考。跟本專案的 _verify_answer() 不同之處：Reflexion 的反思跨任務延續，本專案的驗證只作用在當下這一次回答，驗證完就結束。

5. 校準：模型的自信準不準

校準（Calibration）：校準良好的模型，說有 90% 把握時，長期統計下來真的約 90% 是對的。LLM 常見問題是過度自信——不管對錯，語氣都一樣肯定，這正是幻覺特別難被察覺的原因：模型從語氣上完全不會露出破綻。

6. LLM-as-Judge：用另一個角度評分

本專案的 _verify_answer() 屬於 LLM-as-Judge 模式的簡化版——用語言模型評估另一段由語言模型生成的內容。完整研究通常用不同於生成答案的模型（或至少獨立呼叫、搭配明確評分量表），降低「自己批改自己考卷」的系統性偏誤。
