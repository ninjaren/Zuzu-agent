🦾 Harness 是什麼

這是你實際會花最多時間寫程式碼的地方——模型是別人訓練好的黑盒子，harness 才是你真正能掌控、也真正容易出問題的部分。

Harness（原意是「馬具」）= 包裹、驅動 LLM 的那層程式碼。馬具存在的意義，是把馬的力量導向拉車、走對的路——沒有馬具，馬力氣再大也只是到處亂跑。

Harness 要負責什麼

  • 🧰 管理工具：準備工具、定義好每個工具的 JSON Schema 讓模型知道怎麼呼叫
  • 🔁 跑迴圈：模型要工具 → 執行 → 結果回報 → 模型想下一步，直到任務完成（下一站把這個迴圈拆更細）
  • 📋 管理對話狀態：記住歷史，每次請求重新整包送過去；本專案把歷史存成檔案（sessions/*.json），重開程式不會遺失
  • 🚦 安全把關：危險操作先問使用者——本專案是在 SYSTEM_PROMPT 裡限制檔案操作範圍
  • 🖥️ 呈現結果：把回應送回前端——本專案透過 Flask
模型 = 只會「想」和「說」；Harness = 把「說」變成「真的去做」的那層。這句話值得你貼在螢幕旁邊——寫到後面細節一多，很容易忘記這個最基本的分工，開始把本該 harness 處理的狀態管理、錯誤處理硬塞進提示詞裡，指望模型自己搞定，結果只會更不穩定。

Harness 不是只有一種寫法

你現在用的 Claude Code、ChatGPT 的 Code Interpreter，還有你自己這個 qwen3_8b 專案，本質上都是某種 harness，差別只在：

項目差異點
工具有哪些讀檔案？上網？操作瀏覽器？開放的能力不同
安全把關的嚴格程度有些動作先問使用者，有些自動放行，規則由設計者決定
怎麼管理對話歷史存記憶體、存檔案、存資料庫，各自選擇不同
用哪個/哪些模型有的綁死一個模型，有的可以換（本專案設計成開放介面）

本專案的 Harness 在哪裡

就是 app.py + agent_runner.py：

  • app.py：Flask 伺服器，接收請求、管理 session 存取
  • agent_runner.py 的 build_messages()：組合系統提示詞、記憶、使用者問題
  • agent_runner.py 的 agent_loop()：迴圈引擎——打電話給模型、判斷工具呼叫、執行、餵回去

工作中真的會踩到的坑

⚠️ 迴圈沒有上限，第一次失控通常發生在你沒在場的時候

如果模型持續要求用工具、沒完沒了，agent_loop() 會一直跑下去——本專案目前還沒加這層保護。小規模測試時幾乎不會發現，直到某次模型卡進一個奇怪的推理迴路，或是工具一直回傳讓它誤以為「還沒成功」的結果，才會意識到少了最大輪數限制。寫 harness 時，這是該優先加的防呆，不是「以後有空再說」的待辦。

⚠️ 把「提示詞裡寫了規則」當成真正的安全邊界

本專案目前把檔案操作範圍限制寫在 SYSTEM_PROMPT，這是軟性約束——依賴模型遵守指令，程式層面沒有強制檢查。這種做法在正常情況下沒問題，但一旦輸入裡混進某種你沒預期到的內容（核心鏈路後面會具體拆解這類風險），軟性約束隨時可能被繞過。真正該做強制檢查的地方，要寫在程式碼裡（像 _safe_path() 那樣），不能只靠「希望模型聽話」。

⚠️ 換模型時以為「介面一樣就沒事」

本專案能換模型只需要改 config.py 的 MODEL 名稱，前提是新模型同樣支援 messages、tools 這套標準 API 格式。容易被忽略的地方是：不同模型對同一個系統提示詞的「服從程度」不一樣，換模型之後，原本調校好的提示詞可能需要重新調整，不是換個名字就能無痛切換——這通常是上線後才會發現的落差，值得換模型後先做一輪行為迴歸測試。

🎓 深入機制（進階，可選讀）

「幫大腦裝上手腳」是好記的比喻，但 harness 對應到 AI 領域一個有正式名稱、有學術論文定義的架構模式。這一節講它的理論基礎、控制流模式，以及安全模型。

1. 形式化定義：感知—決策—行動迴圈

經典教科書《Artificial Intelligence: A Modern Approach》（Russell & Norvig）裡，Agent 被定義為：「任何能透過感測器感知環境、並透過致動器對環境採取行動的實體」：

agent: percept_sequence → action

Harness 正是這個抽象定義的具體實作——模型扮演決策函式，harness 負責接上真實世界的感測器（工具結果、使用者輸入）和致動器（工具呼叫）。這跟自駕車背後的感知→決策→行動迴圈是同一個架構模式，只是決策函式換成了 LLM。

2. ReAct 範式：Reasoning + Acting

本專案 agent_loop() 的結構，對應學術文獻裡明確命名的模式 ReAct（Yao et al. 2022）：

Thought → Action → Observation → Thought → Action → Observation → ... → Final Answer
ReAct 概念本專案對應
Thoughtthink=True 時模型產生的推理過程
Actionmsg["tool_calls"]
Observation{"role": "tool", "content": result}
迴圈終止if not msg.get("tool_calls")

ReAct 的關鍵發現：讓模型邊想邊做，比「先規劃完整計畫再一次執行」更能即時根據新資訊調整方向，也更不容易因為一步錯導致全盤皆錯。

3. 工具呼叫的形式化本質：約束生成

一般文字生成是在整個詞彙表上取樣；工具呼叫用 JSON Schema 當形式文法，把輸出限制在合法函式呼叫這個子空間，學術上叫 Structured Output / Constrained Decoding。

這也是為什麼每個工具都要定義完整 DEFINITIONS——不只是給人看的文件，是真正限制模型「能合法說出什麼」的邊界條件。

4. 狀態表示：Transcript 作為「信念狀態」

messages 扮演整個系統的狀態，但嚴格來說不是馬可夫狀態——因為必須攜帶完整歷史，不是只有最新一筆。這是 LLM 無狀態的必然代價：harness 只能把全部歷史當成每次都要重新提供的輸入，模擬出「有記憶」的效果。

5. 三種控制流模式比較

模式特徵適合情境
ReAct（本專案）邊推理邊行動，每步重新評估任務路徑不確定
Plan-and-Execute先產生完整計畫再逐步執行任務結構清楚、步驟可預先列出
Reflexion加入失敗後自我反省的記憶層需要多次嘗試的任務

6. 安全模型：最小權限原則

對應資安領域的最小權限原則：系統只被授予完成任務所必需的最小權限。常見分層：

  • 🟢 唯讀操作：通常自動放行
  • 🟡 可逆操作：可能自動放行，但記錄軌跡
  • 🔴 不可逆或高風險操作：強制要求明確確認

更嚴謹的系統會在程式層面做強制檢查，而不只是寫在提示詞裡——這是防禦縱深（Defense in Depth）：不能只靠提示詞，程式碼本身也要有一道防線。

🛡️ 這裡只是起個頭，完整的權限分級設計、隔離機制、Prompt Injection 防範，見獨立主題頁 AI 代理人安全邊界。
