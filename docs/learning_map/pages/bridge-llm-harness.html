🔌 LLM 和 Harness 中間發生了什麼

這三層（API、Tokenizer、工具呼叫格式）平常被各家 SDK 包得很乾淨，你幾乎感覺不到它們存在——直到出問題的那一刻，不懂這三層,你會卡在不知道哪裡壞掉。

LLM（只認得數字 token）
   ⬆️⬇️ API（整包對話傳過去，收回應）
   ⬆️⬇️ Tokenizer（文字 ⇄ 數字 互轉）
   ⬆️⬇️ 工具呼叫格式解讀（判斷輸出是「說話」還是「要用工具」）
Harness

第一層：API

大腦跑在遠端服務裡（本專案是本機的 Ollama），harness 在你的程式碼裡，兩邊只能靠 HTTP 請求對話。每次請求都要把系統提示詞、完整歷史對話、可用工具清單整包傳過去——模型沒有記憶力，每次都要重講一遍。請求打完拿到回應，這次互動就徹底結束，伺服器端不會留住任何狀態。

一次完整請求長什麼樣（簡化版）

POST http://localhost:11434/api/chat
{
  "model": "qwen3:8b",
  "messages": [
    {"role": "system", "content": "你是 ZuZu..."},
    {"role": "user", "content": "今天台北天氣如何？"}
  ],
  "tools": [...可用工具清單...],
  "stream": false
}

回應也是一包 JSON，裡面有 message.content（要說的話）或 message.tool_calls（要呼叫的工具）。

第二層：Tokenizer

大腦只認得數字（token），不認得「正常文字」。Harness 說話前，翻譯機把文字變成數字；大腦想完吐出一串數字，翻譯機再轉回文字。這一層通常不用你自己動手——Ollama、OpenAI 這類服務都把它包在伺服器側。理解它存在，能解釋幾件你遲早會遇到的事：

  • 🔢 token 數量限制從哪來：context window 上限，這也是本專案要控制 RECENT_TURNS 的原因之一
  • 💰 為什麼雲端 API 按 token 計費：每個 token 都要經過模型運算，運算量才是真正成本
  • 🈶 為什麼中文常常比英文「貴」：同樣意思的句子，中文切出來的 token 數常比英文多

第三層：工具呼叫格式

模型不會真的按按鈕呼叫工具，它吐出一段特殊格式的文字（通常是 JSON），例如：

{
  "tool_calls": [
    {
      "function": {
        "name": "get_current_time",
        "arguments": {}
      }
    }
  ]
}

Harness 收到後判斷「這是要呼叫工具的指令」，才真正執行對應的 Python 函式。模型完全不知道執行發生了什麼——它只是學會「在這種情境下吐這種格式，通常會換到有用的結果」。

對照本專案的程式碼

resp = requests.post(
    OLLAMA_URL,
    json={"model": MODEL, "messages": messages, "tools": TOOLS, "stream": False, "think": think},
    timeout=120,
)
msg = resp.json()["message"]
messages.append(msg)

if not msg.get("tool_calls"):
    # 大腦沒有要求工具 → 這是最終回答
    ...
else:
    for tc in msg["tool_calls"]:
        name = tc["function"]["name"]
        args = tc["function"]["arguments"]
        result = run_tool(name, args)
        messages.append({"role": "tool", "content": result})

requests.post(...) 是那通「電話」，msg.get("tool_calls") 判斷要不要呼叫工具，run_tool(name, args) 才是真正執行工具的那行。模型自己連 run_tool 存在都不知道。

工作中真的會踩到的坑

⚠️ 把「每次都重傳整段歷史」想得太理所當然

對話一長，你會發現回應變慢、甚至開始超過 context window 被截斷——這不是 bug，是上面講的「API 無狀態」的直接後果。本專案限制 RECENT_TURNS = 10 正是為了這個；如果你在自己的專案裡沒設這個上限，遲早會在某次使用者聊很久之後才發現問題，而且那時候通常已經有人在抱怨了。

⚠️ 相信模型吐出來的 JSON 一定合法

Ollama 有時候會把工具參數包成字串而不是物件，本專案用 if isinstance(args, str): args = json.loads(args) 處理這個狀況。但這只是其中一種「格式沒有完全照你預期」的情形——不同模型、不同版本，吐出來的格式細節都可能有落差。沒包 try/except 直接上 json.loads()，遇到一次真正壞掉的輸出，整個請求就直接炸掉使用者畫面，而且很難從錯誤訊息猜到真正原因。

⚠️ 把「工具定義」寫得太隨便，模型就會亂猜參數

工具的 JSON Schema 不是寫給人看的文件，是真正在限制模型「能合法說出什麼」。description 寫得模糊、參數型別沒標清楚，模型就會憑機率亂填——這種錯誤不會讓程式崩潰（格式依然合法），卻會讓工具用錯目標、查錯資料，而且因為沒有報錯，你很容易忽略這其實是個 bug，只覺得「它今天怪怪的」。

🎓 深入機制（進階，可選讀）

「打電話＋翻譯機＋格式判讀」這三層各自都有正式的技術規格。這一節講 Tokenizer 真正的切字演算法、Chat API 的標準化歷史，以及工具呼叫背後的約束解碼機制。

1. Tokenizer 的真正演算法：BPE

現代 LLM 最常用 BPE（Byte Pair Encoding），最早由 Sennrich et al.（2016）引入 NLP 領域。訓練過程大致是：

1. 先把所有文字拆成最小單位（單一字元） 2. 統計整個訓練語料裡「哪兩個相鄰單位最常一起出現」 3. 把這對單位合併成一個新的 token 4. 重複步驟 2-3 數萬次，直到詞彙表達到目標大小（例如 32,000 或 150,000 個 token）

常見的詞因為出現頻率高，很早就被合併成單一 token；罕見的詞則被拆成好幾個小片段——這也是為什麼專有名詞、生僻字常被切得特別碎，它們在訓練資料裡不夠常見，沒機會被合併。qwen3 系列實際用的是 BPE 的變體（結合 SentencePiece），原理相同。

2. Chat API 格式：一個事實上的產業標準

本專案送給 Ollama 的 {"role": ..., "content": ...} 格式，源自 OpenAI 2023 年 Chat Completions API 確立的訊息格式，廣泛採用後變成事實標準（de facto standard）——幾乎所有本地部署工具（Ollama、llama.cpp、vLLM）都相容，這也是本專案能「開放介面、之後換模型」的技術基礎。

Role正式語意
system設定行為邊界與人設，理論上優先權最高，實際約束力取決於模型訓練時多重視這個角色
user使用者（或代表使用者的系統）的輸入
assistant模型自己先前生成的內容，包含文字回答和工具呼叫請求
tool工具執行後的回傳結果，地位類似觀察到的環境回饋

3. 工具呼叫的真正機制：Constrained Decoding

生成文字本質上是在整個詞彙表上做機率取樣，但工具呼叫要求輸出合法 JSON。業界常見解法是 Constrained Decoding（約束解碼）：

在生成每一個 token 時，根據「目前為止已經合法生成的部分」和「JSON Schema 規定的文法」， 動態計算出「下一個 token 只能是哪些候選」，把不合法選項的機率強制設為 0， 再從剩下合法的候選裡依照原本的機率分佈做正規化取樣

這讓模型結構上不可能生成語法錯誤的 JSON，但不保證語意正確——呼叫錯工具、填錯參數值都還是會發生，這是結構約束和內容正確性的根本差異，也是上面「工作中真的會踩到的坑」最後一條的理論根源。

4. Chat API 的協定性質：Stateless Request/Response

這是刻意為之的 Stateless（無狀態）設計，跟 HTTP 協定哲學一致：每個請求攜帶完整上下文，伺服器不需要記住任何先前狀態。好處是可擴展性——請求可以分配給任何有空的機器處理，不用保證「同一使用者的請求送到同一台機器」。
