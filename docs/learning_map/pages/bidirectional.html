🔁 Harness 是雙向溝通的迴圈

多數人第一次寫 agent loop 時，會下意識把它想成「問一次、答一次」——這個假設撐不過第一個需要用工具的任務。它是一個持續來回的迴圈，直到任務結束才停。

Harness ──(傳球：對話內容+工具清單)──▶ LLM
Harness ◀──(回球：想說的話 或 想用的工具)── LLM

方向一：Harness → LLM

每次請求，harness 都要把一整包東西塞過去：

  • 📜 系統提示詞（整個對話中固定不變）
  • 💬 目前為止所有對話紀錄（短期記憶 + RAG 撈回的相關舊對話）
  • 🧰 現在能用的工具清單（連同每個工具的參數格式）
  • 📂 工具執行後的結果（讓模型知道「你剛才要求的事，結果是這樣」）

方向二：LLM → Harness

模型吐回來的東西，可能是：

  • 💭 一段要給使用者看的文字
  • 🔧 一個（或多個）工具請求

Harness 判斷要怎麼處理：給使用者看的就顯示；是工具請求就執行，把結果再傳回去（又回到方向一）。這個來回持續到模型某一輪不再要求任何工具為止。

一輪一輪看整個過程

假設你問：「幫我把檔案裡的錯字改掉」

第1輪：
Harness → LLM：「使用者說要改錯字，你可以用 Read/Edit 工具」
LLM → Harness：「我要用 Read 讀 file.txt」

第2輪：
Harness 真的去讀檔案，拿到內容
Harness → LLM：「這是檔案內容：『今天天氣很好拉』」
LLM → Harness：「我找到錯字了，我要用 Edit 把『拉』改成『啦』」

第3輪：
Harness 真的去改檔案
Harness → LLM：「改好了」
LLM → Harness：「任務完成，跟使用者說一聲」

每一輪，harness 傳給模型的對話內容都比上一輪多一截——多了剛才工具執行的結果。模型不知道自己正在第幾輪，它每次看到的只是一份完整到目前為止的對話紀錄，然後決定下一步。

對照本專案的迴圈結構

while True:
    resp = requests.post(OLLAMA_URL, json={...})     # Harness → LLM
    msg = resp.json()["message"]                      # LLM → Harness
    messages.append(msg)

    if not msg.get("tool_calls"):
        return msg["content"]                          # 沒有工具請求 → 迴圈結束

    for tc in msg["tool_calls"]:
        result = run_tool(tc["function"]["name"], tc["function"]["arguments"])
        messages.append({"role": "tool", "content": result})   # 結果塞回去，進入下一輪

while True 就是這個來回迴圈，messages 是雙方溝通累積出來的完整紀錄。

Harness 更像是模型的眼睛和耳朵——把世界發生的事（檔案內容、工具結果、使用者新輸入）餵回去，這樣模型才知道接下來該怎麼辦。這是個來回不停的迴圈，不是模型發一個命令就結束了。

工作中真的會踩到的坑

⚠️ 沒設上限，第一次代價通常是帳單或當機

如果模型一直要求用工具、沒完沒了，迴圈會一直跑下去。嚴謹的系統要加「最大輪數」限制（例如 20 輪沒結束就強制停止並回報），避免真的卡死。本專案目前的 agent_loop() 沒有這層保護——小規模測試很難暴露這個問題，等到工具種類變多、某個工具偶爾回傳一個模型會誤判成「還沒成功」的結果，迴圈才會真的跑飛，而且常常是在你最沒空處理的時候發生。

⚠️ 把同步阻塞寫法當成理所當然，直到使用者量上來

目前的迴圈是序列執行——一個工具跑完才跑下一個，requests.post() 整個卡住直到拿到回應。單人使用感覺不出差異，一旦有多個使用者同時在跑，這種阻塞寫法會讓每個請求互相排隊等待，延遲會明顯堆疊起來，而且症狀是「整體變慢」，不容易一眼看出是哪一段程式碼造成的，通常要靠量測才能定位。

⚠️ 一輪裡同時呼叫好幾個工具，沒處理「其中一個失敗」的情況

msg["tool_calls"] 本身是個清單，模型可能一次要求呼叫好幾個工具，本專案用 for tc in msg["tool_calls"] 依序執行。如果清單裡第二個工具失敗（例如網路逾時），目前的寫法會直接讓整個請求噴例外中斷，第一個工具已經執行完的副作用不會回滾，模型也不會知道「有一半成功、一半失敗」。這種部分失敗的情境在工具變多之後很常見，值得提早想清楚要怎麼處理，而不是等真的炸了才補。

🎓 深入機制（進階，可選讀）

這一節把迴圈變成正式的狀態機定義，並討論終止條件、平行執行語意、錯誤處理這些工程上必須處理的細節。

1. 正式狀態機：Agent 迴圈的三個狀態

把 agent_loop() 畫成有限狀態機：

[Deciding] --模型要求工具--> [Acting] --工具執行完畢--> [Observing] --結果塞回 messages--> [Deciding] [Deciding] --模型沒有要求工具--> [Done]

唯一出口是 [Done]，也就是模型在某一輪 Deciding 時判斷不需要再用工具。只要模型持續判斷「還需要」，狀態機就持續在 Deciding → Acting → Observing 循環，這是下一節「會不會卡死」的根源。

2. 訊息角色的正式語意

messages 清單的每則訊息，是在記錄狀態機走到現在這一步的完整軌跡。role="tool" 格外關鍵——整個系統裡唯一由外部世界而非模型或使用者產生的內容，形式上扮演強化學習裡「環境回饋」的角色：Agent 採取行動後，環境回饋一個觀察結果，Agent 根據結果決定下一步。

3. 終止條件與「停機問題」的現實版本

電腦科學裡的停機問題（Halting Problem）：不存在通用演算法能對「任意程式在任意輸入下會不會停止」給出正確答案。Agent 迴圈面臨類似的實務困境——沒辦法從邏輯上證明模型一定會在有限輪數內停止呼叫工具。實務解法不是解決理論問題，而是加務實的保護：

  • 🔢 最大輪數：超過 N 輪強制中斷並回報
  • ⏱️ 逾時：本專案 requests.post(..., timeout=120) 對單次呼叫做了保護，但沒對整個迴圈做總時間上限
  • 🔁 重複偵測：連續幾輪呼叫完全相同的工具和參數，很可能卡在循環裡，可以主動中斷

4. 工具呼叫的執行語意：序列、平行、冪等

  • ⚡ 序列 vs 平行執行：沒有相依關係的工具呼叫理論上可以平行，縮短總等待時間；有相依關係就必須序列。本專案統一序列執行，簡單但不是最快
  • 🔄 冪等性（Idempotency）：執行一次和執行多次結果一樣，稱為冪等。讀取類工具天生冪等；寫入類工具不冪等，重試機制若意外重複呼叫，可能造成非預期副作用

5. 錯誤處理：重試與退避

如果 requests.post(...) 因網路或服務暫時無回應失敗，嚴謹系統通常不直接放棄，而用 Exponential Backoff（指數退避）：第一次失敗等 1 秒重試，再失敗等 2 秒、4 秒……每次倍增，一方面給系統恢復機會，一方面避免在服務不穩定時持續發請求讓情況更糟。本專案目前沒有內建重試邏輯，app.py 在最外層用 except requests.exceptions.ConnectionError 直接捕捉並回報，屬於「失敗就立即告知」而非「自動重試」的策略。
