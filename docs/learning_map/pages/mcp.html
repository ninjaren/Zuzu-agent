🧩 MCP 是什麼

MCP（Model Context Protocol）是 AI 工具界的統一插頭規格——理解它能省掉多少重複工作，比理解它的規格書本身更重要。

以前每個工具都要工程團隊自己寫一套專屬連接方式，無法共用。有了 MCP，只要工具做成 MCP 插頭形狀，任何支援 MCP 的系統都能直接插上去用。

沒有 MCP 之前的世界

假設你同時想讓系統連上 GitHub、Notion、公司資料庫，在 MCP 出現之前，每種連接都要自己寫一套專用轉接程式：

Harness A 要連 GitHub → 寫一套 GitHub 專用的程式碼
Harness A 要連 Notion  → 再寫一套 Notion 專用的程式碼
Harness B（別的系統）想連 GitHub → 沒辦法重用 Harness A 寫好的，要重寫一遍

每多一個 harness、每多一個工具，連接方式的組合就呈倍數成長。

有了 MCP 之後

GitHub 團隊寫一個「GitHub MCP Server」
Notion 團隊寫一個「Notion MCP Server」
→ 任何支援 MCP 的 harness（不管是誰寫的）
   都可以直接插上這些 MCP Server 來用，不需要各自重寫連接邏輯

這是標準化的威力——把 N 個 harness × M 個工具的組合爆炸問題，簡化成「每個工具只要做一次 MCP 版本」。

Harness 跟 MCP 差在哪

HarnessMCP
是什麼整個系統，決定何時用工具、要不要先問使用者一種連接規格，像插頭/接頭
由誰決定行為Harness 開發者協定本身，大家共同遵守
能不能換每套系統的 harness 邏輯通常不同標準統一，理論上到處通用

Harness 決定什麼時候用工具、用哪個工具；MCP 只負責連接，不負責決策。

MCP 能提供的不只是工具

  • 🧰 Tools：可以被呼叫執行的函式
  • 📄 Resources：可以被讀取的資料，不需要執行，單純提供內容
  • 💬 Prompts：預先定義好的提示詞模板

🎉 整條鏈串起來

LLM
  ⇄ API + Tokenizer
  ⇄ Harness（管工具、跑迴圈、把關安全）
  ⇄ MCP Client + Transport + JSON-RPC
  ⇄ MCP Server
  ⇄ 真正的工具／資料

工作中真的會踩到的坑

⚠️ 看到「標準協定」就假設「不用再測試」

MCP 標準化的是訊息格式，不是每個 MCP Server 的實作品質——不同團隊寫的 MCP Server，錯誤處理、逾時行為、回傳資料的一致性都可能有落差。接上一個標準協定不代表可以跳過整合測試，這個誤解很容易讓人在正式串接時才發現對方的 Server 行為跟文件寫的不一樣。

⚠️ 把「有 MCP」當成萬用解答，不管規模值不值得

MCP 的價值在「共用」和「隔離」，不是每個工具都因為接了 MCP 就自動變好。只有你自己用、不需要跟外部系統共用的工具，直接寫函式往往比接 MCP 更快上線、更容易除錯——先判斷你是不是真的需要那個「標準化」，再決定要不要多繞這一層。

🎓 深入機制（進階，可選讀）

MCP 是一份有正式規格書的協定，設計上明確借鏡既有的協定工程經驗。這一節講它的分層模型、核心原語的正式定義、生命週期，以及信任模型。

1. 協定分層模型

跟 TCP/IP 的分層思維一樣，MCP 疊在既有的基礎協定之上：

層負責什麼具體技術
應用層定義工具、資源、提示詞這些語意MCP 自己的 method 定義
訊息格式層定義請求/回應/通知怎麼配對JSON-RPC 2.0
傳輸層訊息怎麼在兩個程序間移動stdio／HTTP + SSE

分層的好處是關注點分離——上層完全不需要知道底層是 stdio 還是 HTTP。

2. JSON-RPC 2.0 規格重點

型態特徵
Request帶 id，期待收到對應的 Response
Response帶相同 id，內容是 result 或 error
Notification不帶 id，單向發送、不期待回應

3. 三個核心原語：誰來決定使用它

原語控制權歸屬特徵
🧰 ToolsModel-controlled模型自己判斷要不要呼叫，可能有副作用
📄 ResourcesApplication-controlled由 harness/使用者決定要不要餵給模型，唯讀
💬 PromptsUser-controlled使用者主動選用的提示詞模板

這個分類讓系統設計者能清楚判斷每種能力該放在哪個信任邊界。

4. 連線生命週期

Uninitialized → Initializing（握手協商能力）→ Operation（正常運作）→ Shutdown

握手正式名稱叫 Capability Negotiation：雙方交換支援的版本和能力，確認交集後才進入 Operation 狀態——跟 HTTP 的 Content-Negotiation、LSP 的握手機制是同樣思路。

5. 信任與安全模型

MCP 規格書定義 User Consent：執行有風險操作前，應用程式應讓使用者有機會核准或拒絕。工具可附加 Annotations：

  • readOnlyHint：不會修改任何狀態
  • destructiveHint：可能造成不可逆變更
  • idempotentHint：重複執行結果一樣

🛡️ 完整的權限分級邏輯、隔離機制、Prompt Injection 防範，見獨立主題頁 AI 代理人安全邊界。

6. 跟其他工具呼叫標準的比較

MCPOpenAI Function Calling Schema
性質運行時協定，兩個獨立程序互相溝通靜態資料格式，怎麼執行由開發者自己寫
工具從哪來動態從 MCP Server 查詢開發者在程式裡寫死傳給 API
可共用性任何支援 MCP 的 harness 都能用同一個 Server每個系統要自己實作對應邏輯

本專案目前走的是 OpenAI Function Calling Schema 這條路——這也是為什麼接 MCP 需要額外寫一層轉換邏輯。
