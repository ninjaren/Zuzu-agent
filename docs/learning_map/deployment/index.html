🏗️ 部署架構分級

從個人電腦的本機部署，到中小企業不同預算級距的 pipeline 設計。所有決策最後都收斂到同一個問題：要不要自己扛推論層。

個人部署的核心優勢是隱私和零邊際成本（只有電費，沒有按 token 計費），代價是效能完全受限於你的硬體——這點「AI 訓練 AI（RSI）」那頁討論硬體可行性時已經攤開講過。

中小企業部署的核心決策點

兩個預算級距的分水嶺，本質上是同一個決策：要不要自己扛 GPU 基礎設施。這是成本結構差異最大的地方——雲端 API 是「用多少付多少」的變動成本，自架硬體是「先砸一筆錢，之後邊際成本趨近於零」的固定成本。預算規模決定了你有沒有本錢玩後者。

工作中真的會踩到的坑

⚠️ 低估自架 GPU 的維運人力成本

硬體採購只是總成本的一部分——GPU 機房需要人盯著溫度、電力、驅動更新、故障排除，這筆隱藏的人力成本常常比硬體本身還貴，而且不會出現在最初的採購預算表上。評估「自架划算還是 API 划算」時，一定要把維運人力算進去，不是只比較硬體總價跟累積 token 費用。

⚠️ MVP 做太大，第一版就想包山包海

100 萬級距的專案最常見的失敗模式，是想一次把所有使用情境都覆蓋，結果預算花完了還沒上線驗證過任何一個場景。先挑一個最窄、最容易量測成效的場景做到能用，用它證明價值，再談擴大範圍——這跟「RAG 評估方法論」提過「不要想著上線前做到完整」是同一個道理，只是放大到整個專案規模。

⚠️ 1000 萬級距沒有提早規劃資料治理和合規

正式導入型專案一旦牽涉企業內部資料或客戶資料，資料治理（誰能存取什麼、資料保留多久、怎麼稽核）常常是上線前才臨時被提出來的需求，這時候架構可能已經不方便回頭加這一層。安全邊界和資料治理要在架構設計階段就一起考慮，不是等功能做完才補。

🎓 深入機制（進階，可選讀）

「自架還是用 API」不是憑感覺決定的，有正式的成本分析框架可以套用；這個決策本身也有一個更通用的名稱，在軟體架構和企業採購領域已經討論了數十年。

1. TCO（總持有成本）計算框架

單純比較「硬體一次性費用」跟「API 累積費用」會低估自架成本。正式的 TCO（Total Cost of Ownership，總持有成本）分析，要把維運人力、電費、機房空間、硬體折舊攤提全部算進去：

月 API 成本 = 月請求數 × 平均 token 數 × 每 token 費率 月自架成本 = (硬體總價 ÷ 攤提年限 ÷ 12) + 維運人力月薪 + 電費 + 機房/頻寬成本 當「月 API 成本」持續大於「月自架成本」，且用量穩定不會大幅下降，自架才開始划算

這個損益平衡點，實務上通常比直覺預期的使用量門檻高很多——因為維運人力是固定成本，用量不夠大的時候，分攤到每次請求的人力成本反而比 API 費率更貴。

2. Build vs Buy：軟體架構裡的經典決策框架

「自己蓋 GPU 基礎設施」還是「用別人的 API」，本質上是軟體工程裡歷史悠久的 Build vs Buy（自建或採購）決策。經典的判斷原則：

  • 🎯 這是不是你的核心競爭力：如果自架推論基礎設施本身不是公司的差異化優勢（大多數中小企業都不是），傾向 Buy（用 API），把工程資源留給真正創造價值的部分（例如領域知識的整理、使用者體驗）
  • 🔒 是否有不能外包的限制：法規要求資料不能出境、極高敏感度的資料，這類硬限制會把決策推向 Build，不管成本划不划算
  • 📈 規模是否夠大、夠穩定：用量小或還在驗證階段，Buy 的彈性（隨時可以降用量、換供應商）比 Build 的沉沒成本更有價值

3. Capacity Planning：預算之外，還要算「量」

部署架構的規模不是只看預算金額，還要做 Capacity Planning（容量規劃）：預估尖峰時段同時有多少使用者、每個請求平均要處理多少 token、成長曲線大概長什麼樣。這些數字直接決定該選哪一層的推論引擎（核心鏈路⑥討論過序列 vs 平行執行的取捨，在企業規模下會被放大成「要不要做負載平衡、要不要多開幾個推論服務實例」），沒有先抓量，不管選自架還是 API，都很容易一上線就卡在容量瓶頸上。
