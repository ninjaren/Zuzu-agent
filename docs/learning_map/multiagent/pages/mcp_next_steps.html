🧩 接上 MCP 生態：具體下一步

現在 qwen3_8b 的工具都是自己手刻的 Python 函式，走 Ollama 原生的 tools 參數。這個方向改的是工具呼叫的底層機制，不是答案驗證方式。

回顧：為什麼要接 MCP

核心鏈路的 ⑦ MCP 插頭規格 提過：MCP 讓工具可以插了就用，不用每個工具都自己重寫一套連接方式。

先問自己：真的需要嗎

  • ✅ 適合接 MCP：你想用的功能已經有別人寫好的 MCP Server，自己重寫一遍沒有意義
  • ❌ 不需要接 MCP：功能很specific、沒有現成 MCP Server，或只有你自己的專案在用——直接寫 Python 函式更快更容易掌控

具體要做的三件事

1. 寫一個 MCP Client

官方 mcp SDK（pip install mcp）已經包好 Client 端邏輯：

from mcp import ClientSession
from mcp.client.stdio import stdio_client

async with stdio_client(server_params) as (read, write):
    async with ClientSession(read, write) as session:
        await session.initialize()                 # 握手
        tools = await session.list_tools()          # 問有哪些工具
        result = await session.call_tool("read_file", {"path": "xxx.txt"})

2. 把 MCP 工具轉換成 Ollama 看得懂的格式

# 概念示意
mcp_tools = await mcp_client.list_tools()
ollama_tools = [convert_to_ollama_schema(t) for t in mcp_tools]

all_tools = TOOLS + ollama_tools

MCP 和 Ollama 的格式欄位名稱、巢狀結構略有差異，需要一個轉換函式。

3. 在 run_tool() 裡加一個分流

def run_tool(name, args):
    if name in TOOL_MAP:              # 原本手刻的工具
        return TOOL_MAP[name](**args)
    elif name in mcp_tool_names:       # 是 MCP 工具 → 轉發給 MCP Client 執行
        return await mcp_client.call_tool(name, args)

agent_loop() 原本是同步寫法，MCP SDK 是非同步，這裡要處理同步/非同步橋接。

值得嗎

只是想用現有工具，不需要接 MCP，手刻方式更輕量。接 MCP 的時機是想用別人已經寫好的 MCP 伺服器，不用自己重寫連接邏輯。

還有最後一個方向：如果你要的不是「驗證更準」或「接上更多工具」，是「它自己持續運作、你只在有空時看紀錄」，那是完全不同維度的問題——下一站 ⑤ Always-on Agent 專門討論這個。

工作中真的會踩到的坑

⚠️ 低估同步/非同步橋接要花的時間

如果對 Python 的 asyncio 不熟，光是把既有同步寫法跟 MCP SDK 的非同步介面接起來，就會比預期花更久——而且這類錯誤的症狀常常不是直接報錯，是「協程沒執行完就被丟掉」這種安靜的失敗，debug 起來特別花時間。評估接 MCP 的工程成本時，這一塊經常被低估。

⚠️ 一口氣把所有工具都改成 MCP，而不是先遷移一兩個

一次性全部重寫，代表測試範圍、風險範圍、回滾難度都一口氣放大——任何一個環節沒接好，整個工具系統一起壞掉。先挑一兩個最想串接外部生態的工具試水溫，確認架構可行再逐步擴大，是比較穩妥的做法，下面的深入機制會有正式的名稱和理論支持。

🎓 深入機制（進階，可選讀）

「要不要把現有工具都改寫成 MCP」是典型的系統遷移問題，軟體架構領域已經累積了成熟的設計模式。

1. Strangler Fig Pattern：漸進式遷移，而非一次重寫

名稱來自熱帶絞殺榕——沿著宿主樹慢慢生長、包覆，最終取代宿主，而宿主過程中始終存活。Martin Fowler 把這個現象借用成遷移策略的正式名稱：新系統逐步包覆舊系統，兩者並存，而不是一次性整個換掉。

第一步：只把最想串接外部生態的那一兩個工具改走 MCP 第二步：其餘原生工具維持不變，run_tool() 裡同時支援兩種路徑並存 第三步：確認新路徑穩定後，再決定要不要繼續遷移，或乾脆維持混合架構

漸進遷移讓你隨時可以停在混合狀態，不必為了架構純粹性被迫做全有或全無的選擇——這正是上面「踩雷」第二條的正式解法。

2. Adapter Pattern：MCP Client 的本質

MCP Client 對應經典設計模式裡的 Adapter Pattern：既有系統期待工具是直接函式呼叫，卻想接上介面不相容的新系統（要透過 JSON-RPC 呼叫），中間插入一層轉接器，兩邊都不需要為了彼此修改原本的設計。這也解釋了為什麼「具體要做的三件事」的第 2、3 步本質上就是在實作一個 Adapter——讓 agent_loop() 不需要知道工具背後是原生函式還是 MCP。

3. 什麼時候「不遷移」才是對的架構決策

YAGNI（You Aren't Gonna Need It）：不要為了「可能有一天會用到」的彈性，預先投入工程成本。只有自己用的工具不需要接 MCP，正是這個原則的具體體現——MCP 的標準化、可共用價值，只有真的要跟外部生態互動時才會兌現，提早投入只是增加複雜度，沒有對應效益。
