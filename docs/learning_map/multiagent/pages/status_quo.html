📍 現況：單一 Harness 自我核查

出發去看四個升級方向之前，先搞清楚現在站在哪裡——不然你很容易為了一個小問題，選了一個改動幅度大十倍的方案。

目前 agent_runner.py 的 _verify_answer() 做的是：同一個 harness、同一顆大腦，問兩次——第一次正常回答，第二次換成檢查員角度重新確認。

def _verify_answer(messages, answer, think):
    verify_messages = messages + [
        {"role": "assistant", "content": answer},
        {"role": "user", "content": "請重新確認以上回答是否正確..."},
    ]
    resp = requests.post(OLLAMA_URL, json={"model": MODEL, ...})
    return resp.json()["message"]["content"]

沒有第二個大腦，沒有第二個 harness，成本低、實作簡單，適合抓明顯算錯、日期錯誤這類隨機性失誤。完整細節看核心鏈路的 ⑤ 自我檢查機制。

為什麼要先搞清楚現況，才看升級方向

接下來的四個方向都是在現況的基礎上做不同程度的擴充：

方向相對現況的改動幅度
② 多數決驗證小幅調整——同一個 harness、同一顆大腦，只是多打幾次電話
③ Multi-agent 分工中到大幅調整——需要設計多個角色、多組訊息歷史、協調邏輯
④ 接上 MCP 生態結構性調整——不是改驗證邏輯，是改工具呼叫的底層機制
⑤ Always-on Agent結構性調整——不是改答案品質，是加一層觸發機制

現況的天花板在哪裡

自己跟自己檢查能抓到的，是模型偶發性的失誤。但抓不到系統性的盲點——如果模型對某個知識點本來就理解錯誤，不管問幾次都會得到一樣錯誤的答案，因為問題不是出在不小心，是出在不知道。

目前決定：保持現狀，先不升級。遇到「單次檢查抓不出來的錯誤」再考慮往下走——選哪個，取決於你遇到的是偶發失誤（→②）、需要分工的複雜任務（→③）、想用別人寫好的工具（→④），還是想要它自己持續運作（→⑤）。

工作中真的會踩到的坑

⚠️ 還沒量過錯誤率就急著選升級方向

最常見的失誤順序是：先覺得「應該要更準」，直接挑一個聽起來最厲害的方案（通常是 Multi-agent），砸了不少工程時間，結果發現原本的錯誤根本不是那個方案能解決的類型。先花半天收集一組常見問題、記錄現況的實際錯誤率和錯誤類型，再對照下面的比較表選方向——這半天通常比白做的那幾天划算得多。

🎓 深入機制（進階，可選讀）

「要不要多花一次 API 呼叫去驗證答案」對應到近期一個熱門研究方向：與其把力氣花在訓練更大的模型，不如在推論當下多花運算，換取更好的答案。

1. Test-Time Compute Scaling：另一條提升品質的路

長期以來 LLM 品質提升的主流做法是訓練時擴大規模：更多參數、更多資料、更多運算。Snell et al.（2024）的研究指出另一條路：在推論當下多花運算——讓模型多想幾遍、多檢查幾次——在特定任務上效果可能比換更大的模型還好，而且成本結構完全不同，不用重新訓練。_verify_answer() 正是這個方向最輕量的實作。

2. 推論時策略的光譜

策略額外運算量核心手段
① 現況+1 次呼叫換個角度重新審視一次
② 多數決驗證+N 次呼叫多條獨立路徑，統計共識
③ Multi-agent 分工+N 次呼叫（角色分化）任務拆解，各自用不同視角處理
④ 接上 MCP 生態不一定增加呼叫次數擴大能做的事，不是提升品質
⑤ Always-on Agent看情境擴大運作時機，不是提升品質

3. 先衡量，再優化

Donald Knuth 的名言「過早最佳化是萬惡之源」在這裡完全適用。在投入任何一個方向之前，先替現況建立一個簡單的評估基準，確認現況真的有明顯的錯誤率問題，再決定該往哪投資工程成本——不是單憑直覺覺得「應該要更準」就貿然加大系統複雜度。
