🤝 Multi-agent 分工：多個 Harness 互相傳話

這是真正的「harness 對 harness」，跟現況（同一個 harness 自己玩角色扮演）是不同等級的架構——也是最容易「為了好看而過度設計」的方向，先確認你真的需要它。

概念

Harness A（配一個大腦，角色：寫程式的工程師）
      ⬌ 互相傳訊息
Harness B（配另一個大腦，角色：審查程式碼的審查員）
      ⬌
Harness C（配另一個大腦，角色：負責統籌協調的主管）

真的有多個獨立運作的 harness，各自連著一顆大腦，透過訊息互相傳遞資料。跟多數決驗證不同的地方：multi-agent 裡每個角色各自有獨立的任務和上下文，不是同一個問題問好幾次，是把一個大任務拆成好幾個小任務分頭進行。

跟「現況」的本質差異

現況Multi-agent 分工
角色數量1 個角色演兩次多個角色各司其職，同時存在
訊息歷史共用同一串 messages每個 agent 通常有自己獨立的訊息歷史
任務切分方式沒有切分，只是重新看一遍大任務拆成小任務，各自負責一部分
適合問題單一問題的正確性驗證需要不同專業角度協作的複雜任務

如果要在 qwen3_8b 專案實作，可能的設計

最簡單的起點：不用開多個 process，在同一個 Flask app 裡跑兩次獨立的 agent_loop，用不同的 SYSTEM_PROMPT 模擬兩個角色：

def dual_agent_loop(messages, think):
    # 第一個 agent：負責回答
    writer_messages = [{"role": "system", "content": WRITER_PROMPT}] + messages
    draft = agent_loop(writer_messages, think)

    # 第二個 agent：負責審查（獨立的 system prompt，獨立的訊息歷史）
    reviewer_messages = [
        {"role": "system", "content": REVIEWER_PROMPT},
        {"role": "user", "content": f"請審查這個回答：\n{draft}"},
    ]
    review = agent_loop(reviewer_messages, think)
    return draft, review

這其實還是同一個 Python 程式裡依序跑兩輪 agent_loop，介於現況和真正 multi-agent 之間的過渡形態——還不是真正的 multi-agent，因為兩個 agent_loop 還是依序執行，沒有真正同時存在、互相溝通。

往真正的 Multi-agent 再進一步：需要加什麼

要素作用常用語言／框架
⚙️ 獨立的執行環境每個 agent 用獨立的 process 或 thread，可以同時運作Python 的 multiprocessing／asyncio；更大規模用 Docker 容器各跑一個 agent
📬 訊息傳遞機制agent 之間怎麼互相通知Redis（Pub/Sub，輕量）／RabbitMQ／Kafka（高吞吐），或直接套 MCP 標準協定
🧭 協調邏輯（Orchestrator）誰決定現在輪到誰講話，通常需要再多一個角色專門統籌Celery（Python 任務佇列＋排程）或自己用 asyncio 寫協調迴圈
🛑 終止條件agent 之間互相丟任務也可能卡死在無限迴圈裡，需要最大輪數或逾時機制純邏輯判斷，不需要額外工具，Python 內建的計數器/timeout 就夠

🛡️ 多個 agent 各自能做什麼、彼此之間的信任邊界該怎麼劃，完整討論見獨立主題頁 AI 代理人安全邊界。

代價

  • 💰 成本更高：每個 agent 都要跑完整的 agent_loop，依序執行會比單一 agent 慢上好幾倍
  • 🧩 複雜度上升：誰先講、資料格式、誰做最終決定、卡住了怎麼辦，出錯的地方變多
  • 🎯 適合情境：任務明確需要分工，每個子任務需要不同的專業角度（例如「寫爬蟲規則」+「驗證資料正確性」拆成兩個 agent）
建議：先從過渡形態（依序跑兩個 agent_loop）開始，確認分工真的有帶來效果提升，再投入更多工程成本做成真正獨立、非同步的 multi-agent 系統。不要為了看起來很厲害而過度設計。

工作中真的會踩到的坑

⚠️ 以為「多一個角色審查」一定會讓品質變好

兩個角色如果共用同一套底層知識和偏誤（同一個模型、類似的提示詞風格），審查者很容易變成只是在附和答題者，而不是真的從不同角度挑出問題——這跟自我檢查機制站提過的「檢查員跟答題者是同一顆大腦」是同一個天花板，只是換了個更複雜的包裝。加了審查角色不代表加了真正獨立的判斷力，上線前值得實際拿幾個案例驗證審查有沒有真的抓到東西。

⚠️ 從過渡形態一步跳到完全非同步架構

真正獨立、非同步、跨 process 的 multi-agent 系統要處理的工程問題（協調邏輯、訊息佇列、終止條件、部分失敗處理）遠比看起來多。沒有先驗證過渡形態確實有效，就直接投入完整架構，常見結果是花了大量時間蓋好整套基礎設施，才發現分工本身對這個任務沒有帶來實質幫助——先小步驗證，再決定值不值得往上蓋。

🎓 深入機制（進階，可選讀）

「多個 Agent 互相合作」不是 LLM 時代才出現的新想法，分散式人工智慧領域早在 1980 年代就在研究這個問題。這一節介紹正式的 MAS 定義、經典協調架構，以及跟現代微服務架構的對照。

1. Multi-Agent System（MAS）的正式定義

經典教材 Wooldridge 的《An Introduction to MultiAgent Systems》裡，MAS 被定義為：由多個自主 Agent 組成的系統，每個 Agent 各自感知環境、各自決策，彼此透過互動共同完成單一 Agent 難以獨立完成的任務。這個定義早於 LLM 數十年，最初研究機器人群體協作、分散式問題求解——本頁的多個 harness 互相傳話，是把這套理論框架套用到以 LLM 為決策核心的新情境。

2. 經典協調架構：Blackboard System

Blackboard（黑板）架構：想像一塊公用黑板，所有 Agent 都能讀寫上面的內容——某個 Agent 能貢獻意見時就把結果寫上黑板，其他 Agent 觀察到相關資訊就接手處理。這跟本頁範例「Harness A 寫程式 → B 審查 → C 統籌」概念相通，只是用訊息直接傳遞取代公用黑板。

3. Orchestrator-Worker 模式：跟微服務架構的對照

「統籌協調的主管」角色在軟體架構裡叫 Orchestrator，搭配多個 Worker——現代微服務架構常見的模式。多代理 LLM 系統跟微服務架構有大量共通的工程挑戰：

挑戰微服務架構的解法Multi-agent 系統的對應做法
服務之間怎麼溝通REST API / 訊息佇列文字訊息傳遞，或像 MCP 的標準協定
某個節點掛掉怎麼辦健康檢查、自動重啟、斷路器逾時偵測、失敗後降級策略
怎麼追蹤整體進度分散式追蹤記錄每個 agent 的輸入輸出，方便除錯

4. 正式的 Agent 通訊協定：FIPA ACL

如果要讓多個獨立 harness 正式互相溝通，學術界有現成標準——FIPA ACL，核心概念來自語言學的言語行為理論：每則訊息不只帶內容，還要標明意圖（inform、request、propose），讓接收方明確判斷該怎麼回應。這跟 MCP 的 Tools/Resources/Prompts 依控制權分類在精神上相通——通訊協定除了傳遞內容，也要傳遞這則內容該被怎麼對待的語意。
