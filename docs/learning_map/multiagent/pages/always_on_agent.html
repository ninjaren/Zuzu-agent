🔄 Always-on Agent：持續運作的代理

前面四個方向都在回答「單次回答怎麼更準」，這個方向問的是完全不同的問題：怎麼讓它自己持續做事，你只在有空時回來看紀錄。

先破除一個常見誤解：「Always-on」不代表 LLM 真的 24 小時不停在跑。讓大腦無時無刻持續運算，成本會高到不切實際。真正一直開著的是外層會主動醒來、觸發大腦的系統，大腦本身還是跟平常一樣：被叫醒時才算一次，算完就停。

三層架構

① 觸發層（Trigger / Scheduler）── 一直醒著，但很便宜
         ↓ 符合條件就喚醒
② Harness（跟核心鏈路③講的一樣）── 重建上下文、跑一輪 agent_loop
         ↓
③ 狀態持久化（State Persistence）── 把這輪結果存起來，等下次醒來再接著用

① 觸發層：便宜地一直盯著

不是 LLM，是普通程式邏輯，常見形式：

  • ⏰ 定時觸發：cron job，「每天早上 8 點醒來檢查一次」
  • 📡 事件觸發：收到新 email、webhook 被打、檔案被修改、收到一則訊息
  • 🔁 輪詢觸發：每隔 N 分鐘檢查一次某個條件是否滿足

設計重點是便宜——只負責判斷現在該不該叫醒大腦，不需要大腦介入就能完成判斷。

② Harness 被喚醒後，跟平常聊天同一套邏輯

觸發層判斷該行動後，接下來就是核心鏈路④的 ReAct 迴圈：重建上下文 → 打電話給 LLM → 決定要不要用工具 → 跑完一輪。關鍵差異只在誰觸發了第一次呼叫——大腦完全分不出「使用者打字」跟「排程觸發」的差別，它永遠只是看著送進來的 messages 想下一步。

③ 狀態持久化：為什麼這一層特別重要

大腦每次被叫醒都是全新的一次呼叫，Always-on Agent 必須在每次醒來之間把進度存下來——不然每次醒來都像失憶重新開始。這通常存在資料庫或檔案裡，下次觸發時先讀回這份狀態，重建成要送給大腦的上下文。

任務來源怎麼決定：三種模式

模式概念取捨
固定排程清單預先列好一組任務，照表操課可預期、好控制，但沒辦法自己發現新該做的事
自主目標只給一個長期方向，每輪自己判斷該做什麼更像真正的 Agent，但行為難預測，需要更強的安全防護
混合大部分時間照表操課，留一段自由時間自己找事做平衡兩者，是最常見的實務起手式

安全邊界：為什麼比平常聊天更重要

平常聊天，危險操作會先問你一聲，因為你在螢幕前面。Always-on Agent 的整個存在意義是你不在場時它也在運作——沒有人能即時按下等一下。能自主做的事範圍一定要比平常對話模式收得更緊，唯讀操作通常是最安全的起手式——就算判斷錯誤，最糟也只是這輪白做了、日誌裡多一條沒意義的紀錄。

🛡️ 完整的權限分級設計、隔離機制、Prompt Injection 防範，見獨立主題頁 AI 代理人安全邊界。

真實案例：OpenClaw

OpenClaw 是 2025 年 11 月由工程師 Peter Steinberger 發布的開源 AI agent，到 2026 年快速竄紅，核心賣點正好對應這一站的原則：完全在本機執行，不把資料送到外部伺服器。

層OpenClaw 的做法
① 觸發層在既有的通訊軟體（WhatsApp、Telegram、Slack、Discord、iMessage）裡傳訊息給它，訊息進來就是觸發訊號
② Harness收到訊息後自主執行多步驟任務——開瀏覽器、跑程式、管理檔案、收發 email
③ 常駐執行persistent background process，一直在電腦上開著等訊息

值得注意的設計：OpenClaw 把「查看紀錄」也包裝成用通訊軟體完成——打開 WhatsApp 問它剛才做了什麼，不需要另外開 log 檔案或網頁介面。把紀錄包裝成熟悉的聊天介面，而不是一份獨立的日誌檔，是個聰明的切入點。

以上 OpenClaw 資訊透過網路搜尋於 2026-10-17 查證（見頁尾來源連結），新興專案的細節可能隨時間變動，建議查看當下最新資料。

對照本專案：qwen3_8b 缺什麼

目前是純請求-回應架構——使用者打字才觸發 agent_loop()，沒有①觸發層，嚴格來說不是 Always-on Agent。要加上這個能力：

要素作用常用語言／框架
排程器當觸發層，判斷什麼時候該醒來Python 的 APScheduler（彈性高）或系統層級 cron（Linux）／工作排程器（Windows）
獨立常駐程式不是 app.py，是另一個一直在背景跑的腳本Linux 可包成 systemd 服務；Windows 可用 NSSM 包成服務，或工作排程器定時啟動腳本
觸發來源轉換把觸發來源包裝成跟使用者輸入一樣的 messages，送進既有的 agent_loop()純 Python 邏輯，既有 harness 邏輯完全不用改
存檔機制記錄每一輪做了什麼輕量選 JSON Lines 檔案；要查詢/統計選 SQLite

工作中真的會踩到的坑

⚠️ 觸發層跟 harness 耦合太緊，之後想換觸發方式要重寫一大片

如果把排程邏輯、觸發判斷直接寫進 agent_loop() 內部，之後想從 cron 改成事件觸發（或反過來），會牽動核心迴圈本身。更穩的做法是讓觸發層只負責「組出一份 messages 丟進去」，跟既有的 agent_loop() 完全解耦——這點在最初設計時容易被省略，覺得「反正先跑起來再說」，等真的要擴充觸發方式才發現兩者黏在一起。

⚠️ 日誌只寫「做了什麼」，沒寫「為什麼這麼做」

事後回頭看日誌時，最常卡住的不是「它做了什麼」（這部分通常有記），是「它當下為什麼判斷該做這件事」——如果沒把觸發原因、當時的上下文一起記下來，你會看著一條條紀錄猜不出邏輯，等於白白浪費了「有空再回來看」這個設計初衷。日誌格式從一開始就該包含觸發原因，不只是結果。

🎓 深入機制（進階，可選讀）

「長時間背景運作、中途可能中斷」這個問題，軟體工程領域有專門的名稱和成熟的解決模式——不是 AI 時代才出現的新挑戰。

1. Daemon / 背景服務：作業系統層級的常駐

持續在背景執行、不需要使用者互動的程式，稱 Daemon（守護行程）（Windows 上對應 Service）。OpenClaw 描述自己是「persistent background process」正是這個概念——從系統開機就啟動，一直存在，透過觸發層被動回應。本專案要做 Always-on 版本，那個獨立常駐程式本質上就是在寫一個 Daemon。

2. Durable Execution：讓長任務撐過中斷

如果 Always-on Agent 在執行跨越多輪、耗時很長的任務，中途當機，任務進度不該全部歸零。工作流程引擎（Temporal、AWS Step Functions）領域有專門解法，稱 Durable Execution：把任務拆成一連串可重現的步驟，每完成一步就把進度寫進持久化儲存，重啟後能從上次中斷的地方接著跑。

3. 冪等性在長時間運作下的重要性

冪等性：執行一次和執行多次結果要一樣。在 Always-on 情境下這格外重要——如果程式在「已經發送通知」但「還沒記錄這件事」的瞬間當機、重啟後重新執行同一步，可能重複發送同一則通知。嚴謹的系統會先寫「我即將做這件事」的紀錄，再真正執行，確保中途中斷重試也不會造成重複副作用——這正是上面「踩雷」第二條的根本解法。

4. Observability：不只是寫日誌

軟體工程裡的 Observability（可觀測性）：系統內部狀態要能從外部被看見。成熟做法會區分三種資料：

  • 📝 Logs：離散事件的紀錄，什麼時候發生了什麼事
  • 📊 Metrics：可統計、可畫成趨勢圖的數字，例如今天總共跑了幾輪、成功率多少
  • 🔍 Traces：單一任務從觸發到完成，每個步驟的完整路徑

個人專案用單純的結構化日誌（每輪一條 JSON，包含時間戳、觸發原因、做了什麼決定、呼叫了哪些工具、結果）已經足夠，不需要一開始就上企業級的 Metrics/Traces 系統。
